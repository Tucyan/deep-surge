# 当前开发方向：Three.js 一层可玩 Demo

当前第一层默认值与相关行为由 [平衡试测 v5](first-layer-balance.md) 补充覆盖：初始饥渴 40、低风险保底、属性战术攻击、前置设施与临时防卫销毁；内容版本 first-layer-v4。下文旧版本及旧数值用于追溯。

更新日期：2026-10-03。状态：第一版五次航行可玩循环已实现；实际测试、路线、试测决策与限制见 [首版记录](../development/first-layer-demo-v1.md)。本文保留开发目标与验收约定。用户已将首要目标由 Unity 原型调整为完成一层 Three.js Demo。

## 1. 首要交付

在现有 `water-era/` 中，把视觉演示升级为可以从起手完整玩到一层结束的 Demo。复用海面、木筏和整体视觉布局，接入真实的物资、AP、节点、战斗、合成和结算。首版默认 5 次航行，最后节点结束、生存结算与弃牌完成后，存活即完成本层；角色生命归零即失败，不再存在船体耐久失败。

当前技术栈为 **JavaScript ES Module + Three.js + HTML / CSS**。规则核心不依赖 DOM、Three.js、动画帧或模型对象，应用层以命令统一改状态。沿用本地 Three.js vendor 和静态 HTTP 启动方式，先不安装前端框架、打包器、服务器或新网络依赖。TypeScript 记法仅用于文档表达数据形状，实际代码可使用 JSDoc。

Unity + C# 保留为后续参考，原契约位于 [Unity 历史架构](unity/architecture.md)、[接口](unity/interfaces.md)、[数据模型](unity/data-model.md)。不在这一阶段并行维护两套规则实现；Three.js Demo 的玩法与可玩性验收完成后，再决定 Unity 的恢复时间与迁移方案。内容 ID、实体生命周期、状态机、命令和固定种子约定继续保留，方便后续迁移。

## 2. 内容边界

规则依据仍为 [整体玩法](../../Deep-Surge-整体玩法设计-v0.1.md) 和 [首版内容](../../Deep-Surge-首版卡牌与节点设计.md)。具体内容优先首版表，不沿用旧演示中的数值和循环手牌。

一层交付应覆盖：

- C01–C24 物资、R01–R08 确定配方、M01–M03 普通怪物、N01–N12 节点；临时战术牌另用 T 类内容定义。
- 七张起手、首次三张补给，手牌容量 10；消耗品和原料真实消失，工具保留，部署移出手牌。
- 每轮随机 2～3 候选、非战斗与补给保底、首次限定遭遇应对门槛，提交后其他候选失效。
- 航行与战斗各自刷新 AP，制作和使用分别收费，准备时可以暂时超限，轮末才弃牌。
- 四航道、固定来敌、可见意图、材料匹配、浸湿/束缚联动、基础指令、残骸、撤退与持久战损；空道意图可惩罚生命/SAN/筏格。
- 一次航行生存结算（饱食、水分各 -10）、筏格外围随机破损/脱落及两轮老化、鲜鱼腐坏、设施生产，暴雨/冷雾/漩涡以及三种航行干预牌。
- 起局、重开、完成与失败页面；信息说明、无效行动提示和结算日志。

不加入 Boss、网格地图、商店、策略、藏品、生物流派、自然物成长、随机高级合成、联机或局外成长。燃烧施加不在当前内容池启用；怪物精神攻击可能使 SAN 归零，因此首版需处理基础崩溃（生命 -6、SAN 回 25），不加入负面藏品。木筏视觉完善不能代替规则循环完成。

## 3. 开发顺序与验证

| 阶段 | 交付 | 验证与进入下一阶段的条件 |
|---|---|---|
| 1. 规则基础 | 定义与实例、固定种子、GameSession、AP、阶段和七张起手 | Node 内置测试证明实体不重复、预览不修改状态、拒绝操作不扣资源 |
| 2. 最短完整循环 | 准备补给、候选选择、R01–R03、普通战斗、生存结算、弃牌及终局 | 用测试内容走完 5 次航行，直接伤害/部署均可获胜，失败与最后轮结算正确 |
| 3. 首版内容完整 | 其余配方和节点、材料门槛、重掷、设施生产、状态联动 | 完成内容引用检查及边界用例，所有公开用途均可操作或有明确禁用原因 |
| 4. 现有画面接入 | HTML 手牌/候选/合成/战斗面板，Three.js 防卫和后勤实体映射 | 浏览器实际验证完整成功局与失败局，按钮、选择、日志与状态一致 |
| 5. 一层试玩验收 | 固定种子复现、两条不同选择路线、操作说明、问题记录 | 两条路线均能完成一层；无重复补给、费用遗漏、材料绕过或弃牌卡死 |

“最短完整循环”是中间交付，不缩减最终 24 卡、8 配方、3 怪物、12 节点的首版范围。非随机测试夹具必须标明为测试配置，不能用固定路线冒充正式随机候选。

规则测试不导入 scene.js；浏览器验证补充 DOM 操作与实际画面。现有 `npm run check` 检查全部非 vendor 模块语法，不能作为完整规则验收；`npm test` 已加入规则与模型测试。种子、参数、每轮 AP、选择、材料处理、生命/SAN 损失、筏格破损/脱落及修补次数写入验证记录。

随机权重、T 类牌池、腐坏结果和部分生命周期仍按 [架构中的试测项](architecture.md) 明确配置；编码时给出可复现的 Demo 默认值，记录设计决策与测试结果。不能以参数尚未平衡为理由隐藏关键规则或无限扩大内容。

## 4. 存档与表现优先级

首要验收是一次完整可玩的本层。可恢复随机状态和 JSON 数据形状从开始保留；浏览器存档端口先有契约，完整自动保存和多存档 UI 可以在本层循环完成后接入，不能占用核心规则的开发优先级。未实现保存时隐藏“继续”或明确提示，并说明刷新会重开，不能显示虚假的读档功能。

手牌、AP、弱点、意图、费用和轮末容量优先清楚表达。已有海面和木筏继续使用，单位可先用简单模型/标识表示；音效、复杂动画、新素材和性能精修放在规则可玩之后。动画不决定扣费、回合或胜负。
