# 展示资产维护规范

版本：v0.1。日期：2026-10-03。配合 [开发规范](conventions.md) 和 [当前资产盘点](asset-inventory.md) 使用。资产包括文件，也包括由代码产生的模型、纹理、Shader、SVG/CSS 装饰和图像裁切。

## 1. 资产分类与事实来源

| 类别 | 权威来源 | 必须维护的内容 |
|---|---|---|
| 程序化模型 | models 工厂模块 + 默认配置 + 视觉种子 | 几何、层级、尺度、锚点、共享资源及碰撞/选择代理 |
| 导入模型 | 可编辑源及导出版本 | GLB、贴图、材质、导出参数、运行映射及验证截图 |
| 文件图片/纹理 | 原图 + 制作/导出流程 | 像素尺寸、透明、用途、色彩空间、派生文件与来源 |
| Canvas 纹理 | 生成模块 + 参数 + 种子 | 分辨率、绘制算法、缓存键、纹理语义和资源释放 |
| Shader/粒子 | 模块源码 + uniform 配置 | 效果参数、版本、质量档、颜色/透明与性能 |
| SVG/CSS 资产 | SVG/样式模块 + 配色配置 | viewBox、展示角色、尺寸及可访问说明 |
| 图集/参考图裁切 | 原图 ID + 区域表 | 左上原点坐标、裁切宽高、缩放映射及使用者 |

内容 DefinitionId、局内 EntityId、视觉 AssetId 必须分开。相同轻弩模型可服务多个 C19 实例；设备实体销毁不等于删除共享模型资产。资源的作者/授权信息按实际已知事实填写，未知就记 unknown/pending，不推测许可证或把“用户提供”自动写成可公开商用。

## 2. 登记格式与版本

运行清单位于 `water-era/dist/assets/manifest.json`，来源记录位于 `water-era/asset-sources/README.md`；已为新增美术包的 18 张独立 PNG 创建，状态为 staged-not-integrated，当前页面尚未读取。既有代码模型、Canvas、裁切和前两包尚未纳入运行清单，继续以 [盘点表](asset-inventory.md) 和包元数据为登记依据。清单可先手工维护，不能为了登记阻塞一层实现。

用户新增 C01–C24 与 N01–N12 的 ZIP 已做只读盘点，详见 [资产包元数据](supplied-asset-packs.json)。包内 manifest.csv 可作为 ID/文件映射输入，但不替代运行清单；其中名字、图片内文字或 README 不得覆盖玩法文档和内容数据。接入前将实际来源、安全提取范围、颜色/alpha 验证与运行路径写入登记。

每项至少有：稳定 assetId、kind、version、status、当前路径或生成入口、用途、来源记录、依赖、运行接入位置及维护说明。文件资产记录字节数和 SHA-256；程序化资产记录模块/工厂/defaultConfig/visualSeed，以及代码提交号，不能对不存在的 GLB 填文件 hash。图片派生变更同时更新原图、裁切信息和使用者。

下面是已有代码资产的**清单形状示例**，不是可加载的已实现 registry。legacy 表示当前仍在旧展示代码中，不表示授权结论：

```json
{
  "schemaVersion": 1,
  "assets": [
    {
      "assetId": "model.raft-cell",
      "kind": "procedural-model",
      "version": "legacy-v1",
      "status": "legacy",
      "generator": {"module": "scene.js", "factory": "makeTile", "visualSeed": 2187},
      "configLocation": "scene.js:makeTile",
      "sourceRecord": "asset-inventory:model.raft-cell",
      "consumers": ["scene.js:initial-raft", "scene.js:expandRaft"],
      "dependencies": ["texture.wood-canvas"]
    }
  ]
}
```

清单内 module/url 以静态服务根 `dist/` 为基准，源位置以代码仓库根为基准并独立标注，不混成一个字段。运行层只接受本地登记资源或明确允许的地址，不通过实体命令加载任意路径。状态约定：legacy（旧演示）、placeholder（占位）、ready（已完成对应验证）、deprecated（替代中）；只有记录过实际运行验证才能记 ready。

初期手工数字版号即可。换文件、生成逻辑、关键默认参数、裁切区域、材质/锚点导致外观或使用发生变化时更新版本及记录。稳定 ID 不因显示名称改变；同 ID 替换资产需检查尺寸、锚点、拾取和状态表现的相容性。

## 3. 程序化 3D 模型

新增工厂输入为配置、视觉随机源和资源上下文，返回 Object3D 根与自身更新/清理信息。不依赖全局 scene/raft，不扣 AP、发牌或更改筏格状态。纯辅助几何与实际资产工厂分开，box/rod/rope 不是每一段绳子都登记成独立内容资产。

统一约定：Three.js 世界 Y 向上、XZ 为水面；世界尺度暂按 1 单位≈1 米维护，程序化旧木筏实际 2.3/2.25 格间距应记入配置，不按视觉强制推断真实米制。场景根变换控制整船摆动；每格局部原点在格中心、甲板基准在局部 Y=0，导入模型以适配根修正原点与缩放，不直接改规则坐标。UV、法线、可见面和阴影应随模型验证。

记录根节点名、可动画部件、挂点、底座边界和局部包围盒。筏格及设备工厂必须能响应 intact/damaged/lost 或 operational 状态：破损有明显标识；停用设备保留但不显示工作；脱落格清除实际拾取代理，不通过仅降低 opacity 留下隐形可点击格。

视觉随机按资产/实体独立派生并保存默认种子。旧 scene.js 全局 seed=2187 的 rand 串行构造会受调用次序影响，只记录为 legacy 行为；拆分后禁止把它当游戏种子或规则布局来源。共享模型配置与各实例动态状态分别管理。

模型升级先保存默认视角基线，再修改工厂/配置并验证。程序化来源应保留代码，不因当前没有 .blend/.glb 就漏记或用截图代替可编辑源。不要求每次将代码模型导出 GLB；确需导出时注明它是派生物，并记录生成入口和对应版本。

## 4. 图片、图集和生成纹理

原图尽量无损保留，运行派生放 `dist/assets/`，制作源放 `asset-sources/`。裁切、缩放、压缩、去背景等步骤记录输入/输出、参数及版本；透明素材保留 alpha，不用 CSS 补救误导出的背景色。

图片元数据记录 width/height、alpha、用途、色彩空间、实际文件大小、文件 hash 和源资产 ID。先按实际屏幕用途控制尺寸：卡牌缩略图不加载无必要的全屏大图；避免每张卡重复创建相同纹理。颜色贴图和发光颜色纹理标为 sRGB；法线、粗糙度等数据纹理不按 sRGB 解码。[Three.js 色彩管理](https://threejs.org/manual/pages/color-management.html)

当前 reference.png 同时用于卡图、目的地缩略图、远景和卡框纹理。迁移时把裁切坐标收敛到一份区域表，明确原始像素矩形与显示缩放，不在 app.js/CSS 各保留一套。保留图集可行，但应检测区域越界、原图尺寸变化和高 DPI 模糊；以后换独立图片时要更新所有 consumer。

手牌文字、AP、材料、风险和其他重要信息由 UI 真实文本显示，不能只依赖截图内已有文字。未经确认来源的参考图继续作为本地原型素材；是否可发布按已有授权事实记录，不能把占位图改名后宣称已解决来源问题。

Canvas 纹理也登记：木纹、天空、灯光晕各有生成模块、分辨率、参数、种子、缓存键和 colorSpace。默认按需创建并缓存，不每帧生成；参数变化需明确更新纹理或重建。颜色图和透明遮罩分别按语义处理，不能给所有 CanvasTexture 盲目套同一设置。

## 5. 导入模型与外部源

已有 `raft-model/raft_v004.blend` 和 `raft.glb` 是独立源资产，当前 Three.js 场景未加载它们。后续接入优先 GLB；GLTFLoader 和相关 addons 必须与本地 Three.js 同版本且路径可由静态服务访问，不能直接写 Unity FBX 路径当浏览器运行资源。

接入前记录：源/导出版本、单位与轴向、原点、包围盒、网格/材质/贴图数量、纹理嵌入或外链、默认姿态、加载失败回退，以及按规则拆分或映射部件的方式。静态整船 GLB 不自动等于可破损/脱落筏格模型，需要独立的 cellId → 节点映射；不可按 Mesh 遍历顺序猜对应格。

源 .blend、导出设置和来源说明应进入明确的可恢复位置：迁入 `water-era/asset-sources/` 并版本管理，或存入指定外部资产仓库/备份并在登记中写恢复位置。根 `.gitignore` 当前排除 `raft-model/`，**本机存在不等于 Git 已备份**；发布前不得只有导出 GLB 而丢掉可编辑源。大型二进制是否用 LFS 按实际尺寸与仓库策略单独决定，本轮不安装或推送。

## 6. Shader、装饰与资源生命周期

Shader 以 .js 导出完整 GLSL 字符串，浏览器原生模块不能直接 import .glsl。参数通过 uniforms/config 维护；禁止新增一连串源码 `.replace()` 调画面。当前海面/涡流的替换链在拆分时整理为唯一最终源码，每一步对比视觉基线。

记录效果目的、光照/颜色转换约定、透明和 depthWrite、几何细分、粒子/灯光数量、质量档与更新频率。动态海面、灯笼、粒子只读视觉时间，降低画质不改变怪物处罚。CSS/SVG 图标、光晕和边框同样维护配色与用途，装饰不可遮挡关键按钮或成为假状态图。

资源所有者必须明确：scene 拥有场景级资源，缓存拥有共享 geometry/material/texture，实体工厂拥有实例私有资源。移除实体先取消动画/异步结果，移出 scene 和 Raycast 映射，再释放其私有资源；共享资源仅在最后引用释放或缓存销毁时 dispose。改变共享材质会影响其他实例，做单实例染色前应明确 clone 与所有权。

geometry、material、texture 和 render target 需要各自释放；Material.dispose 不替代 Texture.dispose，移除 Object3D 也不释放 GPU 缓存。清理时避免重复 dispose；停用/破损格上的设备仍存在，其资源不能提前当作已销毁释放。[Three.js 资源释放说明](https://threejs.org/manual/pages/how-to-dispose-of-objects.html)

## 7. 新增、替换、删除流程

1. 查询现有登记，确认能否复用；创建稳定 ID，并记录用途、来源及占位/正式状态。
2. 保存可编辑源或生成入口，产出运行资源，登记尺寸/参数、版本和依赖。
3. 通过资产映射接入展示层，不在规则定义中引入 Texture/GameObject/路径逻辑。
4. 固定视觉种子、相机、分辨率和质量，验证默认、选中、破损/停用、移除等适用状态；记录请求错误与加载时间。
5. 模型/Shader 修改记录几何和 draw calls 等实测值，图片修改检查裁切、alpha 和 UI 可读性；重复创建/销毁检查资源趋势。
6. 更新所有调用、盘点/清单及必要截图。替代旧资产后先标 deprecated，引用清零且新版本验证完成再删除旧运行资源；原始制作源按可恢复策略保留。

基准截图须记录场景、相机、画质、画布分辨率、视觉种子、取样视觉时间、状态 fixture 与资产/代码版本。截图比较不能用动态时间任意变化的两帧来判回归。证据目录只保留有结论的代表图和报告，临时渲染缓存不充当运行资产。

## 8. 后续资产检查入口

拟定 `check:assets` 检查 manifest schema、ID 唯一、文件存在、相对路径/大小写、hash 和图片尺寸、裁切越界、本地依赖闭合、deprecated 引用及 runtime 指向源目录的问题。程序化工厂入口是否存在与资产可否正确渲染要分开验证：静态检查不能替代实际 GPU 场景。

性能和预算以基准实测为依据，不能从文件体积推导 draw calls，不能从静态代码把场景当前帧三角面或 GPU 资源量记为“已测”。代码来源盘点、文件尺寸测量、截图验证和完整玩法试玩四种证据应分别标记。
